# Symptoms: what went wrong, why, and what to change

Read this when an alert fired or a call failed and you want the cause and the change, on Halo's side and on the server's.

One row per alert kind (the read-only watcher's rules, ported to Halo in R2) and per parked bug. The Halo-side column is what the steward may change itself; the server-side column is only ever recommended, with the exact line and what it costs. A conversation that outgrew its window is answered by compaction and a window that holds the prompt; a smaller window is the answer to a spill, never to an outgrown conversation. [S34][S37]

Server lines are written as `NAME=value`. On Windows Ollama reads the user's environment variables: quit Ollama from the task bar, set the variable in Settings (search "environment variables") and start Ollama again; on a Mac use `launchctl setenv NAME value` and restart the app, on Linux an `Environment="NAME=value"` line under `[Service]` in `systemctl edit ollama.service`, then `systemctl daemon-reload` and `systemctl restart ollama`. [S1]

|------|---------|-------|------------------|----------------------------|
| `prompt-trimmed` | "truncating input prompt limit=L prompt=P" | the prompt passed the window the request asked for; the runner kept about half the window. L = num_ctx - (num_ctx - keep) / 2, so L=2050 means the request asked for 4,096: either the conversation outgrew the window or the request carried a smaller window than the host holds [S4][S30] | send the measured window (the learned cap or a tuned twin), at least the prompt's own estimate; compact when the prompt is past the cap [S32][S33] | none for Halo's own calls; for clients that send no window, `OLLAMA_CONTEXT_LENGTH=32768` (costs: every load's KV cache is sized to it) [S2][S5] |
| `reply-cut` | "stop processing: ... truncated = 1", `done_reason` / `finish_reason` "length" | the window filled while the reply was written: the prompt left too little room, and context shift is off for multimodal and hybrid models [S13][S15][S30] | keep a reply reserve (`num_predict` and a prompt at most the window minus the reserve); compact; mark the reply as cut [S13][S37] | none: context shift cannot be turned on for these models; `OLLAMA_KV_CACHE_TYPE=q8_0` makes a larger window affordable (costs: a very small precision loss) [S1][S13] |
| `window-full` | "decode: failed to find a memory slot for batch of size 1" | the KV cache had no free cell for the next token, mid-reply; on the measured host at 64,825 tokens of a 65,536 window, in the draft step [S14][S30] | the same as `reply-cut`: a reply reserve and compaction [S13][S37] | as for `reply-cut` [S1] |
| `no-user-query` | "chat prompt error ... no user query found in messages", HTTP 500 | Ollama dropped old messages from the front to fit `num_ctx`; what was left held only tool results, and the Qwen 3.5 family's renderer refuses that [S5][S6][S7] | compact so the last user message and its tool results fit; send a window that holds the whole prompt [S6][S33] | none [S6] |
| `retry-loop` | the same request fails again and again (several 500s from one client) | a request that cannot succeed is resent unchanged: a prompt still past the window, or a load that never ends [S30][S34] | one recovery per turn, and change the request before resending it: compact, the measured window, a longer load wait [S34][S37] | none [S34] |
| `http-500` | `\| 500 \|` on a request line | on the measured host 16 of 21 came right after a chat prompt error; 4 of the other 5 sit next to "srv stop: cancel task": the request ended while its prompt (up to 44,000 tokens) was still being read or the slot was busy [S5][S30][S38] | read the lines around it: act on `no-user-query` for a chat prompt error; for a cancelled prompt read, wait at least as long as the prompt takes at the host's measured prompt speed [S30][S32] | none [S30] |
| `client-gave-up` | `\| 499 \|`, "client connection closed before llama-server finished loading, aborting load" | the client's timeout was shorter than the load (4.3 s on the measured host); the abort throws the load away, so a quick retry starts the load from zero again [S4][S30] | wait for a first load at least the load budget (locally 20 s + 4 s per GB, over the network 40 s + 6 s per GB) and never retry faster than a load takes [S32] | `OLLAMA_KEEP_ALIVE=30m` keeps a model loaded between calls (costs: its memory is held while idle) [S1][S2] |
| `load-failed` | `msg="Load failed"` | `context canceled` is the client's abort (see `client-gave-up`); any other error is the runner's: out of memory, an incompatible file [S3][S4] | for the abort a longer load wait; for out of memory a smaller window or another host [S3][S32] | out of memory: `OLLAMA_MAX_LOADED_MODELS=1` (costs: every switch of model reloads) [S1][S3] |
| `cpu-spill` | `/api/ps` `size_vram` under `size`; fit "N overflowing"; "offloaded a/b layers" with a under b | llama.cpp's `--fit` moved layers off the GPU to keep its margin, or another program holds the card [S4][S12][S30] | when the arithmetic says the window fits with every layer, send `num_gpu` = every layer (a tuned twin); otherwise a smaller window [S32][S33] | `halo ollama tune <model> --host <name>` makes a twin with every layer on (costs: no disk; a fixed window per twin); `OLLAMA_KV_CACHE_TYPE=q8_0` halves the KV cache (costs: a very small precision loss); `LLAMA_ARG_FIT_TARGET=512` halves the margin (costs: less room for spikes) [S1][S4][S12][S32] |
| `gpu-memory` | "out of memory", "cudaMalloc failed", "CUDA error", "runtime OOM detected" | the card is held by another model or program (an image job), or the window's cache and compute buffer passed it; Ollama itself retries once with a smaller automatic window or after unloading the others [S3][S34] | ask on another host or wait for the other job; a smaller window for this model [S3][S36] | `OLLAMA_GPU_OVERHEAD=<bytes>` keeps room for the other program (costs: that memory is lost to every model); `OLLAMA_MAX_LOADED_MODELS=1` [S2][S3] |
| `stall` | no request progress for 5 minutes | a long prompt read by a slow or spilled model, a request queued behind another (one slot), or a runner that hangs [S1][S3][S34] | read `/api/ps` and the prompt speed; flag a slow box; a hung host is reported, not resent to [S9][S32] | restart Ollama when `/api/ps` stops answering; `OLLAMA_NUM_PARALLEL=2` serves two at once (costs: the KV cache doubles; the Qwen 3.5 family stays at one slot) [S1][S3] |
| `slow-load` | a load running for more than 3 minutes | large weights read from disk (mmap is off for Windows CUDA loads); a load may stall up to `OLLAMA_LOAD_TIMEOUT` (5 minutes) [S2][S3][S34] | keep the request open until the load ends; never abort it [S4] | `OLLAMA_KEEP_ALIVE=-1` keeps the model loaded (costs: its memory is held for good) [S1][S2] |
| `server-down` | `GET /api/version` does not answer | the server is not running, crashed, or the network is down [S9][S34] | mark the host down and ask the next host for the model [S36] | start Ollama again (the tray app; on Linux `systemctl restart ollama`) [S1][S8] |
| `other-error` | any other `level=ERROR` line | read the message; "error loading llama server" is a failed start of the runner [S3][S34] | report it with the line [S34] | none until the message names a setting [S34] |
| `queue-full` | HTTP 503 | more requests than `OLLAMA_MAX_QUEUE` (512) are waiting [S1][S2] | send fewer calls at once to that host [S1] | `OLLAMA_MAX_QUEUE=1024` (costs: callers wait longer instead of failing fast) [S1][S2] |
| `compaction-not-firing` | a session passes the window without compacting, then `prompt-trimmed` or `no-user-query` follows | parked bug 1: the compaction trigger does not fire for the window actually sent [S37] | compact per model at 80 % of the window sent, before the call [S37] | none [S37] |
| `no-reply-reserve` | `reply-cut` or `window-full` on a long session | parked bug 2: the prompt is allowed to fill the window, so the reply has no room [S13][S37] | a `num_predict` reserve and a prompt at most the window minus that reserve [S13][S37] | none [S37] |

## Where the watcher's guide and the sources part ways

- The guide reads every `prompt-trimmed` as an outgrown conversation; `limit=2050` lines on the measured host were a 4,096 window asked for by a client, so a larger window sent was the fix, not only compaction. [S4][S30][S34]
- The guide says "retry once the model is loaded" for a 499; the 499 itself aborts the load, so a client with a short timeout never sees it loaded. [S4][S30][S34]
- The guide answers `cpu-spill` with "a smaller window or free GPU memory"; on the measured host the spill was llama.cpp's margin, and forcing every layer on kept the window. [S12][S32][S34]
- The guide's "server-down" line and its stall rule are its own (they read `/api/version` and the log's progress); nothing in Ollama's log says either directly. [S34]
