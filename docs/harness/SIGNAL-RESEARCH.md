**Daemon and JSON-RPC flags.** The real `signal-cli daemon --help` of the 0.14.9 native binary (run 2026-10-11) is: `--dbus`, `--dbus-system`, `--bus-name`, `--socket [SOCKET]`, `--tcp [TCP]`, `--http [HTTP]`, `--sse-keepalive-interval SECONDS`, `--no-receive-stdout`, `--receive-mode {on-start,on-connection,manual}`, `--ignore-attachments`, `--ignore-stories`, `--ignore-avatars`, `--ignore-stickers`, `--send-read-receipts`. `signal-cli jsonRpc --help` is: `--ignore-attachments`, `--ignore-stories`, `--ignore-avatars`, `--ignore-stickers`, `--send-read-receipts`, `--receive-mode {on-start,on-connection,manual}`. Global flags (from `signal-cli --help`): `-d/--data-dir` (alias `-c/--config`), `-a/--account` (alias `-u`), `-o {plain-text,json}`, `--service-environment {live,staging}`, `--trust-new-identities {always,on-first-use,never}`, `--disable-send-log`, `--log-file`, `--scrub-log`, `-v`. **[changed]** versus 2026-10-02: `--sse-keepalive-interval`, `--no-receive-stdout` and `--receive-mode on-connection` are in the flag list now; the man page still says jsonRpc accepts only `on-start, manual`, but the binary accepts all three ([man page](https://github.com/AsamK/signal-cli/blob/v0.14.9/man/signal-cli.1.adoc), [DaemonCommand.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/src/main/java/org/asamk/signal/commands/DaemonCommand.java)). Defaults: `--socket` is `$XDG_RUNTIME_DIR/signal-cli/socket`, and if `XDG_RUNTIME_DIR` is unset the code falls back to the JVM temp dir ([IOUtils.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/src/main/java/org/asamk/signal/util/IOUtils.java)); `--tcp` defaults to `localhost:7583`; `--http` to `localhost:8080`; `--receive-mode` to `on-start`. At least one of socket/tcp/http/dbus is required. A daemon started without `-a` serves every local account and adds `account` params plus `register`, `startLink`, `finishLink`. The daemon also accepts a socket inherited from the parent (systemd socket activation) via `System.inheritedChannel()` in DaemonCommand.java.

**Two ways to drive it.** (1) `signal-cli -a ACCOUNT daemon --tcp 127.0.0.1:PORT` (or `--socket`, `--http`): many clients, the daemon outlives the bridge. (2) **[new in this write-up]** `signal-cli -a ACCOUNT jsonRpc`: the bridge spawns signal-cli as a child and talks newline JSON over its stdin/stdout -- no socket, no port, no file to protect, same method set, one client only ([signal-cli-jsonrpc(5)](https://github.com/AsamK/signal-cli/blob/v0.14.9/man/signal-cli-jsonrpc.5.adoc)).

**HTTP mode** ([man 5 page](https://github.com/AsamK/signal-cli/blob/v0.14.9/man/signal-cli-jsonrpc.5.adoc), [HttpServerHandler.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/src/main/java/org/asamk/signal/http/HttpServerHandler.java)): `POST /api/v1/rpc` (single or batch), `GET /api/v1/events` (SSE; optional `?account=` filter by number or ACI), `GET /api/v1/check`. **[new]** Every SSE event has an `id`; signal-cli keeps the last 1000 events in memory and a reconnect with a `Last-Event-ID` header replays everything after that id (all kept events if the id is unknown). The server answers HTTP 421 to a request whose `Host` header is not allowed (rebinding guard).

**Method surface** (every CLI command is a same-named method; camelCase params; list-valued params take one value or an array): `send`, `sendTyping`, `sendReceipt`, `sendReaction`, `sendPollCreate/Vote/Terminate`, `remoteDelete`, `listIdentities`, `trust`, `listDevices`, `removeDevice`, `addDevice`, `updateAccount`, `listContacts`, `updateProfile`, `setPin`, `removePin`, `submitRateLimitChallenge`, `getAttachment`, `block`, `unblock`, `sendSyncRequest`, `version`; JSON-RPC-only extras `subscribeReceive`, `unsubscribeReceive`, `startLink`, `finishLink`, `listAccounts`; `register`, `verify` and `link` are CLI-only in single-account mode, and a daemon started without `-a` adds `register`, `startLink` and `finishLink`. Source of the list: the subcommand list printed by `signal-cli --help` on 0.14.9 and the [man page](https://github.com/AsamK/signal-cli/blob/v0.14.9/man/signal-cli.1.adoc). Voice-call commands (`startCall`, `acceptCall`, ...) exist and are irrelevant here.

**Exit codes and JSON-RPC error codes.** Process exit codes ([man page](https://github.com/AsamK/signal-cli/blob/v0.14.9/man/signal-cli.1.adoc)): `1` user-fixable, `2` unexpected, `3` server/IO, **`4` sending failed due to an untrusted key**, **`5` server rate limiting**, `6` CAPTCHA rejected. **[new]** Over JSON-RPC the same classes arrive as negative `error.code` values: `-1` user error, `-3` IO error, `-4` untrusted key, `-5` rate limit, `-6` captcha rejected, plus the standard `-32600 .. -32603`, and `-32603` for unexpected errors; `error.data` carries the per-recipient send results ([SignalJsonRpcCommandHandler.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/src/main/java/org/asamk/signal/jsonrpc/SignalJsonRpcCommandHandler.java)). A send maps to `-4` only when every recipient failed with an identity failure, and to `-5` only when every recipient was rate limited ([SendMessageResultUtils.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/src/main/java/org/asamk/signal/util/SendMessageResultUtils.java)). Per-recipient result types are `SUCCESS, NETWORK_FAILURE, UNREGISTERED_FAILURE, IDENTITY_FAILURE, RATE_LIMIT_FAILURE, INVALID_PRE_KEY_FAILURE`, with optional `token` (captcha challenge) and `retryAfterSeconds` ([JsonSendMessageResult.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/src/main/java/org/asamk/signal/json/JsonSendMessageResult.java)). The bridge must key on the JSON-RPC `code`, not on message text.

## 2. Registration and linking

Unchanged in substance since 2026-10-02. Captcha registration: solve at the signalcaptchas.org registration page from the same network, pass the `signalcaptcha://...` token to `register --captcha`, then `verify CODE` ([wiki: Registration with captcha](https://github.com/AsamK/signal-cli/wiki/Registration-with-captcha), [man page register section](https://github.com/AsamK/signal-cli/blob/v0.14.9/man/signal-cli.1.adoc)). `--voice` works only after an SMS attempt. **[new]** `register --recovery-key KEY --totp TOKEN` recovers an account from the Account Key and Recovery Key shown by Signal Android (man page, same file). A rate limit is lifted with `submitRateLimitChallenge --challenge TOKEN --captcha signalcaptcha://...`; the `token` for it arrives in the failed send's result (`JsonSendMessageResult.token`). Registering a number deactivates it on any phone that held it.

**Linking** ([man page link/addDevice](https://github.com/AsamK/signal-cli/blob/v0.14.9/man/signal-cli.1.adoc), [wiki: Linking other devices](https://github.com/AsamK/signal-cli/wiki/Linking-other-devices-(Provisioning))): `signal-cli link -n NAME` prints a `sgnl://linkdevice?...` URI (the 0.14.9 release note says the man page was updated because "signal-cli prints the QR code itself"); `link` must not be given `-a`; `addDevice --uri` runs on a primary device; up to five linked devices. **[new]** 0.14.9 links accounts that have no phone number: the account is then identified by its ACI, `listAccounts` returns `aci` with a null `number`, and in multi-account mode the `account` param must be the ACI ([signal-cli-jsonrpc(5)](https://github.com/AsamK/signal-cli/blob/v0.14.9/man/signal-cli-jsonrpc.5.adoc)). In daemon JSON-RPC mode linking is `startLink` -> URI -> `finishLink {deviceLinkUri, deviceName}`.

**Registration lock.** `setPin` / `removePin`; `verify --pin` ([man page](https://github.com/AsamK/signal-cli/blob/v0.14.9/man/signal-cli.1.adoc)). Signal's side: with a registration lock on, a forgotten PIN can lock the number for up to 7 days and the lock expires after 7 days of inactivity, after which the number can be re-registered ([Signal support: Re-registering using your Signal PIN](https://support.signal.org/hc/en-us/articles/5440120029082-Re-registering-using-your-Signal-PIN) -- direct fetch returned 403 on 2026-10-11; the 7-day figures are from the search-result text of that article read the same day, and the 7 days restart whenever the account is used from a linked device per a third-party guide). Practical rule for the dedicated number: set a PIN on it and store it with the other secrets.

## 3. Limits and the shapes the bridge codes against

**Message size [changed: now a number].** `MAX_MESSAGE_SIZE_BYTES = 2000`, measured as UTF-8 bytes ([ServiceConfig.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/lib/src/main/java/org/asamk/signal/manager/config/ServiceConfig.java)). When a send's text is longer, `ManagerImpl.applyMessage` sends the first 2000 bytes (split on a character boundary) as the visible body and uploads the **entire** text as an extra attachment of type `text/x-signal-plain` ([ManagerImpl.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/lib/src/main/java/org/asamk/signal/manager/internal/ManagerImpl.java), [AttachmentHelper.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/lib/src/main/java/org/asamk/signal/manager/helper/AttachmentHelper.java), [MimeUtils.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/lib/src/main/java/org/asamk/signal/manager/util/MimeUtils.java)). Official apps show that as a "read more" text file. So a 2000-byte chunk is a hard line for a plain bubble.

**Receiving long text.** On the receive side signal-cli downloads a `text/x-signal-plain` attachment and substitutes its content for `message` in the JSON ([IncomingMessageHandler.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/lib/src/main/java/org/asamk/signal/manager/helper/IncomingMessageHandler.java), [MessageEnvelope.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/lib/src/main/java/org/asamk/signal/manager/api/MessageEnvelope.java)). That whole step sits inside `if (!receiveConfig.ignoreAttachments())`, so **`--ignore-attachments` also turns off long-prompt inlining**: a long prompt typed on the phone would arrive cut at about 2000 bytes.

**Attachment caps.** Receive side: signal-cli refuses to download an attachment over `MAX_ATTACHMENT_SIZE = 150 * 1024 * 1024` bytes (ServiceConfig.java, same file). Send side: no client-side cap exists in the source; the limit is enforced by Signal's servers and is not published in any file read. Unresolved, see section 7 question 3.

**Typing and receipts.** `sendTyping` (params `recipient` list / `groupId` list, `stop` boolean): the indicator lasts 15 seconds unless a STOP is sent ([man page](https://github.com/AsamK/signal-cli/blob/v0.14.9/man/signal-cli.1.adoc), [SendTypingCommand.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/src/main/java/org/asamk/signal/commands/SendTypingCommand.java)). `sendReceipt` (params `recipient`, `targetTimestamp` list, `type` = `read` default or `viewed`, [SendReceiptCommand.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/src/main/java/org/asamk/signal/commands/SendReceiptCommand.java)). `--send-read-receipts` on the daemon sends read receipts automatically for all incoming data messages (delivery receipts are always sent). `send` also takes `--note-to-self`, `--notify-self`, `--no-urgent` (no push), `--text-style start:length:STYLE` with `BOLD, ITALIC, SPOILER, STRIKETHROUGH, MONOSPACE` in UTF-16 code units, `--edit-timestamp`, `--quote-*`, and `--view-once` (man page, send section).

## 4. Identity and verification

**`listIdentities`** (params: `number` = any recipient form -- phone number, ACI, `PNI:uuid`, or `u:username`) returns, per known key, `{number, uuid, fingerprint, safetyNumber, scannableSafetyNumber, trustLevel, addedTimestamp}`; `trustLevel` is `UNTRUSTED`, `TRUSTED_UNVERIFIED` or `TRUSTED_VERIFIED`; `safetyNumber` is the 60-digit grouped string; `scannableSafetyNumber` is base64 of the QR bytes; `number` is null when the contact is known only by ACI ([ListIdentitiesCommand.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/src/main/java/org/asamk/signal/commands/ListIdentitiesCommand.java), [TrustLevel.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/lib/src/main/java/org/asamk/signal/manager/api/TrustLevel.java), read 2026-10-11). **`trust`** takes `recipient` plus either `verifiedSafetyNumber` (the plain digits or the base64 QR bytes) or `trustAllKnownKeys` ([TrustCommand.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/src/main/java/org/asamk/signal/commands/TrustCommand.java), [man page](https://github.com/AsamK/signal-cli/blob/v0.14.9/man/signal-cli.1.adoc)).

**What each `--trust-new-identities` mode does** (all from [IdentityKeyStore.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/lib/src/main/java/org/asamk/signal/manager/storage/identities/IdentityKeyStore.java), `isTrustedIdentity` and `saveNewIdentity`, read 2026-10-11) **[new, and it matters for pairing]**:
- `always`: every key is trusted.
- `on-first-use` (default): the first key seen for a recipient is stored `TRUSTED_UNVERIFIED`. A later different key is, on a **receive**, reported untrusted (the message is not delivered); on a **send** it is stored as `UNTRUSTED` and the send fails (JSON-RPC `-4`, CLI exit 4).
- `never`: the first key seen for a recipient is also stored `UNTRUSTED`. So a stranger's very first message cannot be decrypted-and-delivered: it does not reach the bridge as text, and a reply to that stranger fails with `-4` until someone calls `trust`.

**What the bridge sees when a message is refused for identity.** A receive notification carries an `exception` object next to the (content-less) `envelope`; the message itself stays in signal-cli's cache for up to 14 days and is retried ([ReceiveHelper.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/lib/src/main/java/org/asamk/signal/manager/helper/ReceiveHelper.java), [UntrustedIdentityException.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/lib/src/main/java/org/asamk/signal/manager/api/UntrustedIdentityException.java), [JsonReceiveMessageHandler.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/src/main/java/org/asamk/signal/json/JsonReceiveMessageHandler.java), [JsonError.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/src/main/java/org/asamk/signal/json/JsonError.java)). Derived from those files, not a captured sample (no live account here):
```
{"jsonrpc":"2.0","method":"receive","params":{"account":"+15555550123","exception":{"message":"Untrusted identity: +15555550101","type":"UntrustedIdentityException"},"envelope":{"source":"+15555550101","sourceNumber":"+15555550101","sourceUuid":"11111111-1111-4111-8111-111111111111","sourceName":"name","sourceDevice":1,"timestamp":1631458508784,"serverReceivedTimestamp":1631458508790,"serverDeliveredTimestamp":1631458508800}}}
```
No `dataMessage` key, so no text. `trust` on a recipient while receiving sets a retry flag that the receive loop checks (`ManagerImpl.trustIdentity` -> `setNeedsToRetryFailedMessages`; `ReceiveHelper` line 131), so the cached message is redelivered after trusting; how soon (immediately or on the next envelope) is not settled by source reading, see 7.A.

**Mapping.** Pin the sender by `sourceUuid` (the ACI) plus the `safetyNumber` read from `listIdentities` at pairing; a later key change shows up as the notification above or as `-4` on send, with no polling loop. Re-verification is `trust` with `verifiedSafetyNumber` set to digits the owner confirmed, never `trustAllKnownKeys`.

## 5. Operational concerns (Kali VM, work VM behind a proxy)

**Network [changed: now exact].** signal-cli's live endpoints are `chat.signal.org`, `cdn.signal.org`, `cdn2.signal.org`, `cdn3.signal.org`, `storage.signal.org`, `cdsi.signal.org`, `svr2.signal.org` (all HTTPS, WebSocket on chat) ([LiveConfig.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/lib/src/main/java/org/asamk/signal/manager/config/LiveConfig.java), read 2026-10-11); `signal.art` and `signal.group` appear for sticker packs and group links. Signal's own firewall guidance is to allow `*.signal.org` on TCP 443 (and UDP for calls), and that a transparent proxy "needs to support WebSockets" ([Signal support: Firewall and Internet settings](https://support.signal.org/hc/en-us/articles/360007320291-Firewall-and-Internet-settings) -- 403 to direct fetch on 2026-10-11, wording from the search result text read that day). No inbound port is needed; the daemon listeners are local.

**Proxy [changed: resolved].** There is no `--proxy` flag in any of the help output captured on 2026-10-11. The code asks the JVM's default `ProxySelector` for the proxy that would be used for an `https://` URL and, if it returns an HTTP or SOCKS proxy, hands host and port (no credentials, `null, null`) to libsignal's `Network.setProxy` ([SignalDependencies.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/lib/src/main/java/org/asamk/signal/manager/internal/SignalDependencies.java) lines 165-198, [Utils.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/lib/src/main/java/org/asamk/signal/manager/util/Utils.java) `getHttpsProxy`). So the standard JVM properties are the interface: `-Dhttps.proxyHost=... -Dhttps.proxyPort=...` or `-DsocksProxyHost=... -DsocksProxyPort=...`, passed through `JAVA_TOOL_OPTIONS` or `JAVA_OPTS`. Whether the GraalVM native binary honours those properties was not tested (no proxy here); on a proxied host use the JVM build.

**Windows and Unix sockets [changed].** The JVM build runs on Windows x86-64 (libsignal DLL bundled, section 1). signal-cli binds `--socket` with `ServerSocketChannel.open(StandardProtocolFamily.UNIX)` ([IOUtils.java](https://github.com/AsamK/signal-cli/blob/v0.14.9/src/main/java/org/asamk/signal/util/IOUtils.java)), which is JDK API and not run here. The Halo side is the real constraint: the Python on this Windows host (3.11.7) has no `socket.AF_UNIX` (`hasattr(socket, "AF_UNIX")` -> False, checked 2026-10-11), and Halo's own cc: tool bridge already switches to a loopback TCP socket plus a per-session token on `os.name == "nt"` for the same reason (`halo_harness/ccbridge/server.py`, removed with the cc: route in 3.1.5.0; `remote/control_socket.py` uses the same transport). So on Windows use `--tcp 127.0.0.1:PORT` (or the stdio `jsonRpc` child), never `--socket`.

**Data directory and logs.** Default `$XDG_DATA_HOME/signal-cli` (`~/.local/share/signal-cli`), overridden with `-d`/`--data-dir`; it holds the account SQLite databases and downloaded attachments ([man page](https://github.com/AsamK/signal-cli/blob/v0.14.9/man/signal-cli.1.adoc), [wiki: Quickstart](https://github.com/AsamK/signal-cli/wiki/Quickstart)). **[new]** The daemon prints every received message to **stdout** unless started with `--no-receive-stdout` (daemon help, 2026-10-11), so under a service manager message text would land in the journal; `--scrub-log` removes numbers and UUIDs from log lines. 0700/0600 permissions on the data dir are Halo's own hardening, not signal-cli's. Back up the SQLite files before upgrading (Quickstart wiki).

**systemd user unit** (illustrative, built from flags in the help output above; upstream ships no unit):

[Service]

## 7. Mapping the brief onto signal-cli, and the nine questions

**Pairing flow, as it can actually run [changed].** The 2026-10-02 flow assumed the first message from a stranger is readable. Under `--trust-new-identities=never` it is not (section 4). Two workable shapes, decision for round 3 (section 8 recommends B): **A** `on-first-use`: the stranger's first message is readable, the bridge answers with the pairing code and pins the safety number; the cost is that the bridge answers a stranger once. **B** `never`: the stranger's first message arrives as the `UntrustedIdentityException` notification (sender ACI visible, no text); the bridge never replies; the owner sees "contact request from <ACI prefix>" in the TUI/CLI, compares the safety number from `listIdentities`, and approves; the bridge calls `trust` with `verifiedSafetyNumber`; the phone then sends the pairing code (or the cached message is redelivered); the sender is pinned on `sourceUuid`.

**Linked-device self-filtering.** In Note-to-Self mode the stream carries the whole account. Keep only an envelope with `syncMessage.sentMessage.destinationUuid` equal to the account ACI; drop everything else without logging or persisting it (shapes in section 3). Start the daemon with `--ignore-stories --ignore-avatars --ignore-stickers` to cut incidental traffic.

## 8. What the brief should change

Mechanics only; the six security layers of the brief stay as written. Each bullet names the finding it comes from. Rounds refer to the brief's four rounds (2 = control socket, 3 = Signal transport and bridge, 4 = CLI/TUI/docs).

- **Pairing under `never` (section 4).** The brief's step "the first message from a sender is answered with a one-time pairing code" cannot happen under `--trust-new-identities=never`: the stranger's first message is undecryptable and a reply fails with `-4`. Recommended (shape B, section 7): the bridge never replies to an unknown sender; the exception notification becomes a "contact request from <ACI prefix>" card in `/remote` and on the CLI showing the safety number from `listIdentities`; the owner approves there; the bridge runs `trust` with `verifiedSafetyNumber`; then the phone sends the pairing code. The pairing code, the identity pin and "nobody else is ever answered" are all kept, and the bridge answers a stranger zero times instead of once. Shape A (`on-first-use`) is the fallback if redelivery after `trust` is not prompt (7.A i). This is the one real decision for round 3.
- **Pin on the ACI.** Accounts and contacts may have no phone number (0.14.9 numberless linking, recipients known only by ACI). `peers.json` keys on `sourceUuid`; `sourceNumber` is stored when present and never used as the identity.
- **Chunking rule (section 3).** The hard line is 2000 UTF-8 bytes per message, not a character count. Chunk at 1800 bytes or less, on whitespace where possible, counting bytes with `len(text.encode("utf-8"))`; never rely on signal-cli's long-text fallback for streamed output. When a reply would need more than about four chunks, send one message with a text attachment instead; signal-cli accepts `data:text/plain;filename=reply.txt;base64,...` as an attachment, so nothing is written to disk by the bridge.
- **Inbound long text (section 3).** `--ignore-attachments` also disables long-text inlining, so a long prompt would arrive cut at about 2000 bytes. Leave attachments on, accept only `text/x-signal-plain` from a paired peer as prompt text, ignore every other attachment type, and delete the downloaded file from the data dir after reading (privacy layer 4: no message content at rest).
- **Flags the bridge always passes (sections 1, 5).** Global: `--trust-new-identities never`, `--scrub-log`, `-d <halo remote dir>/signal-cli`. Daemon or jsonRpc: `--no-receive-stdout` (daemon only), `--ignore-stories --ignore-avatars --ignore-stickers`. Not passed: `-v`, `--send-read-receipts` (it acks every incoming data message, including ones the bridge is about to refuse; the bridge sends its own `sendReceipt` after the peer and signature checks).
- **Windows transport (sections 1, 5).** The Windows host needs the JVM build with JRE 25 on x86-64 and cannot use a Unix socket from Python. Use the spawned `signal-cli -a ACCOUNT jsonRpc` child over stdio as the default transport on every OS (no listener, no port, no socket file; this also strengthens layer 5 on the signal-cli side), and `daemon --socket` (POSIX) or `daemon --tcp 127.0.0.1:PORT` (Windows) only for the service-manager install where signal-cli must outlive the bridge. Linux x86-64: native tarball; Linux arm64 and macOS: JVM build, with a libsignal caveat on arm64 Linux.
- **Error mapping (section 1, 4).** The brief's "exit code 4 / 5" becomes: JSON-RPC `error.code` `-4` (CLI exit 4) = identity changed or untrusted, refuse and notify in both places; `-5` (exit 5) = rate limit, pause sending for `retryAfterSeconds` and surface `token` as a captcha card; `-3` = network, reconnect with backoff; `-1` = user error, show the message to the owner; `-6` = captcha rejected. Additionally the changed-safety-number refusal also fires on the **receive** side as an `UntrustedIdentityException` notification, so the refusal notice needs no polling of `listIdentities`.
- **Typing and receipts (section 3).** `sendTyping` lasts 15 seconds: re-send every 10 seconds while a turn runs and send `stop:true` at `turn_done`. `sendReceipt type=read` once a command passes the checks.
- **Reconnect and stale commands (section 7.A ii).** Prefer `--receive-mode manual` with `subscribeReceive` from the bridge so signal-cli leaves messages on Signal's server while the bridge is down; the existing 5-minute timestamp window then rejects stale commands. If 7.A (ii) shows messages are dropped in `on-start` mode instead, keep `on-start` and document that commands sent while the bridge is down are lost. With `--http` the SSE `Last-Event-ID` replay (last 1000 events) is available as a third option but needs the HTTP listener, which the brief rules out.
- **Rendering polish (section 3).** `send` takes `textStyle` ranges such as `start:length:MONOSPACE` in UTF-16 code units; code fences can be rendered as real monospace spans (compute offsets from `text.encode("utf-16-le")`). Optional.
- **Proxy and egress (section 5).** The setup text for a proxied VM: use the JVM build and set `JAVA_TOOL_OPTIONS=-Dhttps.proxyHost=... -Dhttps.proxyPort=...` (HTTP or SOCKS, no credentials); `halo doctor` lists the seven `*.signal.org` hosts to allow and that a transparent proxy must pass WebSockets.
- **Version pin and verification (section 1).** Pin 0.14.9 in setup, check the `.asc` signature shipped beside each archive when `gpg` is present, and have `halo doctor` warn at 90 days from the pinned release date.
- **Test fixtures (section 1).** The release publishes `signal-cli-0.14.9-json-schemas.tar.gz` (one schema per receive payload class). Round 3's fake signal-cli server should build its envelopes from the shapes in section 3 and check key names against those schemas rather than invent them.
- **Registration (section 2).** Set a registration-lock PIN on the dedicated number and store it in `~/.halo/remote/`; 7-day lock window per Signal. Voice fallback only works after an SMS attempt. The VoIP question stays open until the number is bought (7, question 5).

**9.2 `events.Command` kinds today** ([halo_harness/events.py](../../halo_harness/events.py) `COMMAND_KINDS`, 12): `user_input`, `interrupt`, `set_mode`, `set_model`, `slash`, `permission_reply`, `question_reply`, `plan_reply`, `steer`, `run_compact`, `run_clear`, **`approval_reply`** (the brief's list of 11 lacks the last). A `Controller` only ever queues `user_input`, `set_model`, `run_compact`, `run_clear`; the others are answered by direct calls, and `Session.run`'s command pump ([agent/loop.py](../../halo_harness/agent/loop.py) around 8340-8400) handles `interrupt`, `steer`, `set_mode`, `set_model`, `permission_reply`, `question_reply`, `plan_reply`, `approval_reply` only as safety nets. `slash` has no branch in the pump at all. So the socket should call Controller methods, not push raw Commands.

**9.3 Event kinds** (`EVENT_KINDS`, 32): `user_message`, `message_start`, `text_delta`, `thinking_delta`, `tool_use_start`, `tool_use_ready`, `tool_progress`, `tool_result`, `permission_request`, `question`, `plan_review`, `todos`, `status`, `message_end`, `error`, `turn_done`, `subagent_start`, `subagent_end`, `subagent_queued`, `subagent_progress`, `replay`, `notification`, `steer_queued`, `steer_applied`, `compaction`, `phase`, `steer_restart`, `governor`, `governor_state_unpersisted`, `system_note`, `status_notice`, `approval_request`. Payloads the feed needs: `permission_request {id, name, input, reason, suggested_rule}`; `question {id, name, input}`; `plan_review {id, plan, path}`; `approval_request {id, position, text, is_error}`; `phase {state, model, ttfb_ms, kind}`; `message_end {stop_reason, usage, cost_usd, context_pct, ...}`; `turn_done {reason}`; `steer_queued/steer_applied {text}`; `notification {text, level}`; `error {message, err_type, retryable}`; `text_delta {text, index}` (coalesce; never forward raw deltas at Signal's pace).

**9.4 How events leave the session.** `Controller.start()` runs `session.run(self.commands, self.events.put, mcp_status_fn=...)` on a daemon thread named `halo-session`, so every event goes through `Controller.events`, a plain `queue.Queue` drained by exactly one consumer (the TUI's `_drain` timer in [tui/app.py](../../halo_harness/tui/app.py), or [ax_mode.py](../../halo_harness/ax_mode.py)). A second reader on that queue would steal events from the TUI. The `subscribe` feed therefore has to be a tee: wrap the emit callable handed to `session.run` (or add a fan-out inside `start()`) so each event is delivered to the queue and to the socket subscribers. **Print mode does not use `Controller`**: `headless.run_print_mode` drives the session with `output.PrintModeSink` / `StreamJsonSink` and a stream-json stdin queue, so "print-mode wiring" in round 2 is a separate adapter and the socket module should depend on a small handle (submit, interrupt, answer, set mode/model, status, subscribe) that both can implement.

**9.5 What the `cc:` route already puts under `~/.halo/run/`** (`halo_harness/ccbridge/server.py` and `halo_harness/agent/cc_runtime.py` line 394, both removed with the cc: route in 3.1.5.0, [halo_harness/providers/local_runtime.py](../../halo_harness/providers/local_runtime.py) line 87):
- The run dir `bridge_home()/run` is created on first `cc:` use and chmod'd 0700 (POSIX only effect).
- `~/.halo/run/<id>.sock`, mode 0600, one per live `cc:` bridge, POSIX only. **`<id>` is a fresh `uuid4()` per bridge, not the Halo session id** (`ToolBridgeServer(session_id=str(uuid4()), ...)`), removed on close, and any stale `*.sock` whose listener is gone is deleted by a connect-probe sweep at the next bridge start. A `<halo-session-id>.ctl` file cannot collide with either, and the sweep globs only `*.sock`.
- Windows (`os.name == "nt"`): no file at all. The bridge binds `127.0.0.1` on an OS-assigned port and a random 16-byte hex token; the child gets `HALO_CCBRIDGE_HOST`, `HALO_CCBRIDGE_PORT`, `HALO_CCBRIDGE_TOKEN`, and the first line of a connection must be `{"token": "..."}` within 5 seconds or the connection is closed. POSIX child env is `HALO_CCBRIDGE_SOCKET=<path>`. This is the pattern the control socket should copy for Windows.
- Wire: newline-delimited JSON `{"id", "method", "params"}` -> `{"id", "result"}` or `{"id", "error": {"message"}}`; methods `tools/list`, `tools/call`, `tools/await_change` (25 s long poll).
- `~/.halo/run/local-servers.json`: the managed-local-model-server registry, not per session.
- Per-session state outside `run/`: the session log `~/.halo/sessions/<project-slug>/<session_id>.jsonl` ([agent/log.py](../../halo_harness/agent/log.py), `session_id` = `uuid4().hex`), which is what `/tail` and `list_sessions` read, and a hooks env file keyed by the session id (`hooks.env_file_path`).
