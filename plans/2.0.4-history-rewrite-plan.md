# 2.0.4 round 1: history rewrite plan

Written from a real `halo audit privacy --history --json` run against
this repo at commit 4a788a3 (2026-10-05). That run's full output (real
paths, real literals, never masked) was written to a scratch path
outside this repo, named in the spawn prompt that produced this plan --
never committed here. Every literal in THIS file is either a masked
placeholder (resolved per step 3) or a string already confirmed, by
hand, to be non-identifying (a generic Windows system-cache path, a
commit hash, a file path inside this repo).

This document is a PLAN only. Writing it does not rewrite history: no
`git filter-repo` invocation, no force-push, and no clone reset happens
as part of producing this file. A human (the orchestrator) executes the
steps below deliberately, after reading them.

## Why

`halo audit privacy --history` found 382 findings across 27 distinct
paths (`junk-path` 4, `home-path` 20, `machine-name` 355, `token` 3 --
4 paths to purge entirely, 23 needing a text replacement; zero
`lan-ip`/`link-local-ip`/`dot-local-hostname`/`email` -- everything of
those kinds was already fixed by the W5/W5b/H14b content-scrub passes,
see `tests/test_privacy_scan.py`). Every one of them is already
FIXED in the current working tree (`halo audit privacy` with no flags
returns 0 on this same commit) -- the problem is purely that git never
forgets: a file deleted with a plain `git rm`, or a line later edited,
is still sitting in every commit before that point, readable by anyone
who clones the repo and runs `git log -p`.

## Step 1: mirror backup (first, always, announced -- never asked)

Before anything destructive, back up the repo exactly as it is now:

```sh
git clone --mirror <path-to-this-checkout> halo-harness-backup-2026-10-05.git
```

Announce this backup exists and where it lives; do not ask permission
to make it -- a backup is never the risky step. Every command after
this one assumes the backup already succeeded.

## Step 2: paths to remove entirely (`--invert-paths`)

Four paths, all four added in commit `5df3502de53e3cfe452b8f298e9bec5f7add3342`
and plainly `git rm`-ed (never purged) in commit
`69cfaede592dac606e0202ad786f0648e26e1cf1` -- a stray Windows shell-cache
folder that should never have been committed. These four path strings
are generic Windows OS-cache artifacts (a system cache database and
three GUID-named cache files under the standard per-machine
`ProgramData\Microsoft\Windows\Caches` location) -- they do not name or
identify the repo's owner, so they are written out literally here
exactly as `halo_harness/privacy_rules.py`'s own `JUNK_PATH_RE` already
spells them in a comment:

```sh
git filter-repo \
  --invert-paths \
  --path '%SystemDrive%/ProgramData/Microsoft/Windows/Caches/cversions.2.db' \
  --path '%SystemDrive%/ProgramData/Microsoft/Windows/Caches/{44CDC051-F44A-4C0C-8237-B85FB225D766}.2.ver0x0000000000000001.db' \
  --path '%SystemDrive%/ProgramData/Microsoft/Windows/Caches/{6AF0698E-D558-4F6E-9B3C-3716689AF493}.2.ver0x0000000000000001.db' \
  --path '%SystemDrive%/ProgramData/Microsoft/Windows/Caches/{DDF571F2-BE98-426D-8288-1A9A39C3FDA2}.2.ver0x0000000000000001.db'
```

No other path in this repo's history needs to be removed entirely --
every other finding is a LINE inside a file that is otherwise wanted
(see step 3).

## Step 3: text replacements (`--replace-text`)

`plans/2.0.4-history-replacements.txt` is the input template, committed
with every left-hand side written as a masked placeholder. Resolve it
into a real, UNCOMMITTED file before running filter-repo:

1. `<HOME_PATH_LEAK.BACKSLASH_FORM>` = the literal `C:\Users\` immediately
   followed by the real account name (resolve the name with
   `python -c "from halo_harness.privacy_rules import REAL_OWNER_USERNAMES; print(sorted(REAL_OWNER_USERNAMES)[0])"`
   run against THIS checkout -- never write the resolved value into any
   committed file). `<HOME_PATH_LEAK.FORWARDSLASH_FORM>` is the same
   name after `C:/Users/` instead.
   **Do not resolve this as the bare account name alone** -- those same
   first few letters are also this project's own old product name and
   public GitHub org (`rolo-claude`/`roloVibes`), which appear
   hundreds of times throughout history on purpose and must not change.
2. `<REMOVED_NAMES[i]>` / `<EXTENDED_SCAN_TERMS[i]>` = run
   `python -c "from halo_harness.privacy_rules import REMOVED_NAMES, EXTENDED_SCAN_TERMS; print(REMOVED_NAMES); print(EXTENDED_SCAN_TERMS)"`
   against this checkout and index in; both tuples are already public
   (committed in this same round), so resolving them needs nothing
   secret.
3. `<TEST_FIXTURE_TOKEN_AT_9f387f1_LINE_22>` = run
   `git show 9f387f1de82c082a32c874dfdeb93f67bd29fbf6:tests/test_session_cli.py | sed -n '22p'`
   and read the `sk-ant-`-shaped value out of that line (a fake test
   fixture for the `--sanitize` feature itself -- `tests/
   test_session_cli.py` no longer exists at HEAD, so this is the only
   way to recover the exact text).
4. Verify the exact `regex:` prefix syntax against the installed
   `git filter-repo --help`/README before running -- correct as of the
   version this plan was written against, but the tool's own docs are
   the source of truth at execution time.

```sh
git filter-repo --replace-text <the-resolved-local-only-file>
```

Twenty-three paths carry at least one of these findings (full list:
`history-audit-204.json`'s `summary.text_replacements`) -- six
`docs/harness/tui-snapshots/*.svg` files and four `plans/2.0.2-round*-
brief.md` files for the home-path leak (backslash in the SVGs, forward
slash in the plan briefs -- confirmed by hand), the rest for the
machine-name terms (`tests/helpers/fake_home.py`, `tests/
test_frontmatter.py`, `tests/test_loop_headless.py`, `tests/
test_mcp_catalog.py`, `tests/test_memory.py`, `docs/harness/
ACCEPTANCE-2026-09-25.md`, `docs/harness/INSTALL.md`, three `docs/
harness/review-findings-*.md` files, and both the current and the
pre-rename path of one provider-catalog module). `--replace-text`
matches by CONTENT, not path, so it finds the same literal at every one
of these without needing the path list spelled out as flags.

**Known, deliberate exception**: `tests/test_privacy_scan.py`'s own
historical revisions contain the home-path literal too (it is the
regression guard that detects it, not a leak) -- `git filter-repo
--replace-text` has no path-scoping, so it WILL also rewrite those old
revisions. This is harmless: the CURRENT (HEAD) revision of that file,
landing in this same round, no longer stores the literal as a
contiguous string in its own source (`halo_harness.privacy_rules.
REAL_OWNER_USERNAMES` is a single bare word, built with string
concatenation, specifically so this rewrite cannot corrupt the live
regression guard). Confirm this with step 5's verification before
trusting it blindly.

## Step 4: tags to re-create

`git filter-repo` rewrites every commit's hash, including every commit
a tag points at. It updates the LOCAL repo's own tag refs to follow the
rewrite automatically, but a force-push of the rewritten branch does
not touch the REMOTE's existing tags -- git refuses to silently move a
remote tag that already exists. Every one of these 15 tags must be
deleted on the remote and re-pushed from the rewritten local repo:

```
v0.3.0  v0.3.1  v0.4.0  v0.4.1  v0.5.0  v0.6.0  v0.7.0  v0.8.0
v1.0.0  v1.0.1  v2.0.0  v2.0.1  v2.0.2  v2.0.3  v2.0.3.1
```

```sh
# after filter-repo has rewritten the local repo and re-added the remote
# (filter-repo removes the origin remote by default, as a safety net):
for t in v0.3.0 v0.3.1 v0.4.0 v0.4.1 v0.5.0 v0.6.0 v0.7.0 v0.8.0 \
         v1.0.0 v1.0.1 v2.0.0 v2.0.1 v2.0.2 v2.0.3 v2.0.3.1; do
  git push origin --delete "refs/tags/$t"
done
git push origin --force --tags
git push origin --force refs/heads/master
```

## Step 6: the two clones to reset

Every existing clone now has a history that diverges from the remote's
new one at every commit -- a plain `git pull` will fail or (worse)
silently create a merge of two unrelated histories. Both of the clones
this project currently has must be reset the same way, not
re-cloned-by-habit-but-actually-merged:

```sh
# the build host's own working checkout:
git fetch origin
git reset --hard origin/master
git gc --prune=now

# the owner's Linux clone:
git fetch origin
git reset --hard origin/master
git gc --prune=now
```

Either clone may instead be deleted and freshly re-cloned if that is
simpler on the day -- both commands land in the same place. A WORKTREE
or an in-flight branch on either clone should be finished or abandoned
before running this (a hard reset discards anything not pushed).
