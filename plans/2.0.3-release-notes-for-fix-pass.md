# 2.0.3 release notes for the fix pass

Follow-ups noticed while verifying each round. Items here are NOT blockers
for the round that found them; the Opus review and the fix pass at the end
of 2.0.3 pick them up (or move them to 2.0.5 hardening with a reason).

## From round 2 (`ol:` provider, 6cf1b52)

- `_build_catalog` runs one `/api/show` per model on the host; fine for a
  handful of models, slow for a host with dozens. Lazy per-model show (only
  for the model in use plus the panel's visible rows) or a parallel fetch.
- Print-mode JSON for a provider error carries `is_error: true` and an
  empty `result`; the message is on stderr in text mode only. Consider
  surfacing the error text in the JSON result as the other dialects do
  (check first whether they do).
- Kali live run of `ol:` against a LAN host is still unverified (the LAN
  host's daemon is loopback-only behind an OpenAI-shaped proxy; needs the
  owner's call). Everything else ran live on the Windows build host.

## From round 3 (host analysis, fit, roles, f97958a)

- `halo doctor` prints `[OK] Ollama (default): not reachable at
  http://127.0.0.1:11434` on a machine with no daemon and no `ollama.hosts`
  entry. A synthesized default host nobody configured should read as a
  neutral note (not OK, not WARN), and a CONFIGURED host that is down should
  be a WARN.
- Lean prompt for small windows: a one-word turn on a 27B model fitted to a
  16384 context costs about 10.2k prompt tokens (about 6.7k of tool
  definitions for the 24 built-ins plus the system prompt). The tool cap
  cannot go below the built-in set. Decision needed in round 6: compact
  tool descriptions + reduced built-in set per context class in 2.0.3, or
  move to 2.0.5 (see the brief's Round 6 bullet).
- Round 6 decision (2026-10-05): the lean prompt above does NOT ship in
  2.0.3 -- moved to 2.0.6 hardening (the slot the 2026-10-05 roadmap
  reorder gave the old "2.0.5 hardening" scope; this note and the brief's
  own Round 6 bullet still say "2.0.5" because they predate that reorder).
  2.0.3 ships the measurement only (the ~10.2k-prompt-token cost above,
  carried into `docs/LOCAL-MODELS.md`'s "known limits" section), not the
  compact-tool-description/reduced-built-in-set fix.
- The fit estimate uses the f16 KV bytes-per-token formula; hosts running a
  quantized KV cache (q8_0/q4_0 via OLLAMA_KV_CACHE_TYPE) have about half
  or a quarter of that footprint, so the fitted context is conservative
  there. Read the cache type back if Ollama ever exposes it, or add an
  `ollama.hosts[].kv_cache_type` hint.
- AMD (rocm-smi / sysfs) and Apple (system_profiler) GPU probes are still
  unconfirmed on real hardware; say so in docs until someone runs them.
- Picker `u` (assign a role) has plain-function tests only; a Textual pilot
  test for the key path would pin the UI wiring.

## From the LAN-host live run (2026-10-04, Kali VM -> the LAN host, after round 4)

- MUST FIX before v2.0.3 (now owned by the brief's Round 5b, "local-model
  excellence"): a REMOTE host with nothing loaded gets no fit
  estimate at all (there is no GPU read and `/api/ps` is empty), so
  `compute_num_ctx` falls back to the 131072 cap and the remote GPU loads
  the model partially offloaded (seen live: a 30B MoE at 19.9 GB of 24.2 GB
  in GPU memory, the rest in system RAM). This is the owner's primary
  setup (Kali VM driving the GPU box). Fix in three parts: (1) a remote
  host whose fit is unknown gets a conservative default cap (32768) instead
  of 131072, with `ollama.hosts[].max_ctx` as the explicit override; (2)
  after the first load, read `/api/ps` back and, when the model shows
  partial offload at the chosen num_ctx, print one plain notice naming the
  `max_ctx` value to set and record it as a learned per-host-and-model cap
  so the next session does not repeat the overload; (3) `/ollama` on a
  remote host shows the learned cap and the suggestion. Pin all three.
- Everything else in that run was right: `halo ollama` from the VM reads
  the remote host, the plain turn and the Read tool round trip complete
  over the LAN, and the offload sentence reported the real numbers.

## From round 5c (find and use model files), live run 2026-10-04

- FIXED before commit: the runtime fetch looked at `/releases/latest`,
  which for llama.cpp is a non-binary release (one asset); the binary
  releases are prereleases tagged `b<number>` with 36 assets, CUDA builds
  need the separate `cudart-...` companion archive, and `digest` is
  `sha256:<hex>`. The selection now lists recent releases and matches by
  pattern, with the CUDA major/minor rule against the driver and Vulkan as
  the small fallback. Reviewer: check the consent sentence names both
  downloads and the total size.
- FIXED before commit: `/api/create` with a `modelfile` body is obsolete
  ("neither 'from' or 'files' was specified"); the import now uploads the
  blob (`POST /api/blobs/sha256:<hex>`) and creates with a `files` map,
  verified live on the build host's daemon (model answered, then deleted).
- FIXED before commit: stopping a managed server left a zombie on Linux
  (SIGTERM without reaping; the stub was a child of the test process), so
  two tests failed on Kali and WSL while passing on Windows. Stop now
  terminates and reaps (held handle, or waitpid plus SIGKILL after a grace
  period), and the liveness check treats a zombie as dead. Reviewer: every
  other child-process stop in the tree (background Bash jobs, the `cc:`
  subprocess, MCP servers) deserves the same zombie check on Linux.
- FIXED before commit (second live run): Ollama stores an untagged name as
  `<name>:latest`, so `ol:<name>` missed its own catalog row (trained
  context, capability, digest) and `num_ctx` fell to the 8192 fallback; one
  name-normalizing helper now serves every comparison. Reviewer: grep for
  any remaining direct `==` on Ollama model names.
- FIXED before commit: Ollama 0.34 returns `400 exceed_context_size_error`
  when the prompt exceeds `num_ctx` (round 2 assumed silent truncation);
  mapped onto the ContextOverflow path with one retry at a larger fitting
  context, else compaction. Reviewer: confirm the retry never exceeds the
  learned cap or the host's max_ctx.
- FIXED before commit: `halo local` in a fresh process did not show a
  served file-backed model or resolve its `hf:local/<name>` ref from the
  managed-server registry.
- Round 6 live item: the served 0.5B test model answered a plain turn
  (10.6k-token prompt, fine) but did not call the Read tool ("I couldn't
  find the file"); with a model that small this is inconclusive. Re-run with
  a tool-capable GGUF (3B to 8B, Qwen or Llama instruct) and check whether
  llama-server needs `--jinja` for the tool-call template; if it does, add
  the flag to the managed runtime's argv.

## From round 5b part 2 (doctor, constrained tool calls)

- FIXED before commit (live defect, 2026-10-04): the first implementation
  constrained every post-tool-result turn to the tool-call schema, so the
  model could never answer in prose and looped on a meaningless tool call
  (175 requests in 25 minutes on the build host). Rule now: constrained
  decoding only inside the repair step, never on a normal turn, plus a
  guard that stops a turn after three identical tool calls in a row on the
  local-model profiles. Reviewer: check that no other path forces a
  schema on a free turn, and that the loop guard's notice is one plain
  sentence.

- `halo ollama doctor` prints "this daemon is reachable from this machine
  only; to share it on the LAN flip the tray app's switch" whenever the
  host URL is loopback, which is the CLIENT's view, not the server's bind:
  on the build host the daemon was already exposed on all interfaces when
  that line printed. For a LOCAL host, read the listening address (Windows
  `netstat -ano`, Linux `ss -ltn`, macOS `lsof -iTCP -sTCP:LISTEN -P`) and
  state the fact ("listening on all interfaces" / "loopback only"); keep
  the hint only for the loopback-only case; for a remote host say nothing
  about it.
- Auto-calibration with step-up on first use loads a 27B model two or
  three times before the first turn (about a minute on the build host).
  Acceptable once per model, but the notice must say how long it will
  take and `--no-up` should be the auto path's default on hosts where the
  first guess already fits, leaving the full step-up to the explicit
  `halo ollama calibrate`. Decide in round 6 after the live timing.

## From round 4 (`hf:` route)

- `tests/test_privacy_scan.py` walks tracked files only, so a worker's NEW
  (untracked) files are not scanned until someone stages them: two
  "Bearer <fake-token>" assertion strings in a new test went unnoticed by
  the worker's own full run and surfaced at review. Make the scan include
  untracked, non-ignored files (`git ls-files --others --exclude-standard`)
  in addition to tracked ones.
- `tests/test_init_cli.py::test_scripted_provider_loop_...` is flaky on a
  clean tree (confirmed by the round 4 worker with a stash); find the
  timing dependency rather than retrying.
- `halo init`'s provider wizard still lists neither Ollama nor Hugging Face
  (round 5 owns the tab; the brief's rounds 2 and 3 text implied Ollama was
  already there -- it was not).
- MUST FIX before v2.0.3 (confirmed live 2026-10-04 with rolo's token): the
  router's `GET /v1/models` is NOT OpenRouter's shape. Each entry is
  `{id, object, created, owned_by, architecture: {input_modalities,
  output_modalities}, providers: [ {provider, status, context_length,
  pricing: {input, output}, is_free, supports_tools,
  supports_structured_output, first_token_latency_ms, throughput,
  is_model_author}, ... ]}` (135 models for this token). The round 4 parser
  reads top-level context and pricing, so it finds none. Fix: derive the
  model's context as the max over `status: live` providers (or the pinned
  provider's when the ref carries a `:<provider>` suffix), price as the
  cheapest live provider's with the provider named, `is_free` when any live
  provider is free, tools and structured-output flags per provider, and
  show throughput and first-token latency as the picker's speed columns
  (the same columns Experiential and 2.0.4 add). Pin with a fixture copied
  from the real shape (no token, no account data). Also read the router's
  `x-inference-provider` response header (seen live: the provider that
  served the call) into the transcript's model line and the cost meter, and
  price the turn from that provider's row; today `halo providers` shows 0
  models and print mode reports no cost for `hf:` turns because of the
  parser gap. Everything else in the live run was right: a plain turn, a
  Read tool round trip and the `:cheapest` suffix all completed through
  Halo's `hf:` route, and the reachability column said reachable.
- Only `HF_TOKEN` is read; `HUGGING_FACE_HUB_TOKEN` and `HF_API_TOKEN` were
  not confirmed as official and are not accepted. Revisit if the research
  doc or a live check confirms them.
