Scope: `git diff v2.0.2 -- <Pass A files>` (36 files, about 9,100 added lines): providers/ollama*.py, local_*.py, gguf_header.py,

## Findings

1. **critical** — `halo_harness/tui/dialogs/ollama_status.py:44-54` + `tui/dialogs/local_status.py:94-98` (pushed by `tui/slash.py:1070-1072,1114-1122`) — Both dialogs define `_render(self) -> None`, which shadows Textual's own `Widget._render()` (the method that returns the widget's Visual). On the first paint of the modal's own background Textual calls `self._render()`, gets `None`, and raises. So `/ollama` and `/local` (no arguments, or `refresh`) take the whole TUI down. Nothing in tests/ or test_tui.py mounts either dialog; the commits verified only `halo ollama`, `halo local` and print mode. — Verified: a Textual 8.2.8 pilot pushing either dialog onto a bare App exits with return_code 1, `AttributeError: 'NoneType' object has no attribute 'render_strips'`, raised from `widget.py` `_render_content` (`visual = self._render()`, `self = LocalStatus()`). — Fix: rename both methods (e.g. `_render_rows`), and add a pilot that mounts each dialog and presses `r`, `s` and Esc.

2. **critical** — `halo_harness/providers/local_runtime.py:328-350` (+ `:286-309`, `:202-204`; called from `controller.py:174-182` and `headless.py:1435-1447`) — Every halo exit (TUI quit, every `halo -p` run, its atexit) sends SIGTERM to every non-kept pid in the shared `~/.halo/run/local-servers.json`. On Windows that is TerminateProcess. There is no check that this process started the server, or that the pid still is a llama-server or mlx_lm.server.
   - A second session's server is killed under it.
   - The documented flow `halo local serve X`, then `halo -p --model hf:local/X`, loses the server after the first answer.
   - A stale entry gets its pid killed whatever process now owns it. Stale entries come from a closed console window, a crash, a reboot, or a `keep: true` entry after a reboot via `halo local stop`. Windows reuses pids quickly.
   - Load, then terminate, then save also drops entries another process added in between.

   — Verified: a scratch registry held one non-kept entry. It pointed at a sleeping child for which this process held no local_runtime handle. `stop_all_managed_servers_except_kept` terminated the child (returncode 15) and emptied the registry. — Fix: record an owner (pid plus process start time) and the server's own start time and command line per entry. Stop only entries this process started. Check that a recorded pid is still the recorded process before signalling it (psutil create_time/cmdline, or `/proc/<pid>/stat` starttime). Serialize registry writes with a lock file.

3. **major** — `halo_harness/providers/ollama_fit.py:193-210` + `gguf_header.py:177-194` + `safetensors_config.py:174-204` — The KV bytes/token formula uses `head_dim = embedding_length / head_count`. It never reads `<arch>.attention.key_length`/`value_length`, which `/api/show` and GGUF carry, or `head_dim` in config.json. For current models the formula undercounts the KV cache, so the fit estimate is up to 2x too large. The docstring claims the approximation only ever errs conservative. This is the root cause of round 5b's live result for the 30B coder: the arithmetic said 65536, calibration found 32768. It feeds the fit estimate, the auto-calibration start, the panel and wizard "what fits" lines, and `halo local serve -c`, which is never calibrated. — Verified: formula vs true ratios:
   - Qwen3-Coder-30B-A3B: 0.500
   - Qwen3-32B: 0.625
   - gpt-oss-20b: 0.703
   - Llama-3.1-8B: 1.0

   With 2 GiB of headroom, 30B-A3B gives 32768 by the formula and 16384 with the true head size. — Fix: use `key_length + value_length` (falling back to `2 * embd/heads`), read `head_dim` from config.json, and pass both keys through `gguf_model_info`.

4. **major** — `halo_harness/providers/ollama.py:327-344` + `agent/loop.py:2444-2445` + `providers/stream.py:140-153,879-910` — The `exceed_context_size` retry ceiling is `min(hard cap, host max_ctx, fit estimate, learned cap)`. It leaves out three bounds:
   - the remote-unknown 32768 default, so a remote host can retry up to 131072, the exact partial offload the LAN-host MUST-FIX removed;
   - the 8192 weights-do-not-fit fallback, so a model whose weights don't fit can retry up to 131072;
   - the trained context. The docstring says this is to avoid asking past it, but leaving it out of the `min` is what allows that.

   FALLBACK_NUM_CTX 8192 is also below Halo's own ~10.2k-token minimum prompt (round 3 note), so every fallback request overflows into this retry. The output budget `num_predict` defaults to 16384 on `ol:`, so the retry jumps at least to `pow2ceil(prompt + 16384)`. — Verified (module runs):
   - remote unknown: num_ctx 32768, ceiling 131072, retry 65536;
   - weights do not fit: num_ctx 8192, ceiling 131072, retry 32768;
   - trained-8192 model with fit 65536: retry 32768.

   — Fix: pass the decision itself. Make the ceiling `min(` the same candidates `resolve_num_ctx_and_source` used, including trained context, remote default and fallback `)`, and size the retry by the prompt plus a small reply reserve. Remember a successful retry for the rest of the session.

5. **major** — `halo_harness/providers/ollama.py:241-307` + `ollama_calibrate.py:280-326` — A local host with no GPU reading gets min(trained context, 131072). That covers CPU-only boxes, a VM, AMD on Windows (no rocm-smi), Intel, and Linux AMD via sysfs (free memory always None). The conservative 32768 default applies to remote hosts only. Auto-calibration on such a box records `does_not_fit`, because `size_vram` stays 0. The notice then says "using the live fit estimate/remote default instead", but neither exists locally, so the model a measurement just proved does not fit gets the largest window. On CPU that is a multi-GB KV allocation in system RAM. — Verified: `resolve_num_ctx_and_source(131072, None, None, remote=False)` returns `(131072, 'trained context')`; a `None` learned cap leaves that unchanged. — Fix: treat "local, nothing known" like remote-unknown (32768, or 8192 for CPU-only), and let a recorded `does_not_fit` select the fallback.

6. **major** — `halo_harness/providers/ollama.py:254-289` — A learned cap replaces a smaller live fit estimate. The same docstring says the round must never let "a bigger host_max_ctx/learned_cap ... win over a SMALLER live fit_estimate (that would risk the exact overload this whole round exists to prevent)". A cap measured on an idle GPU therefore keeps applying when another workload holds VRAM later (an image server, a media transcoder), and the session loads partially offloaded with only the chip marker to show for it. — Verified: `resolve_num_ctx_and_source(131072, None, 16384, learned_cap=65536)` returns `(65536, 'learned cap')`. — Fix: keep both in the `min`, or let the cap replace only an unloaded-model arithmetic estimate, never a live free-memory reading that is smaller. Then correct the docstring or the commit claim, whichever loses.

7. **major** — `halo_harness/providers/tool_call_schema.py:81-97` + `agent/loop.py:4651-4658` + `doctor_local.py:209-212` + `gym_send.py:209-220` — Every caller passes `local=is_local_host(host)`, which is loopback-only (`ollama_hw.py:404-412`). The gate's own docstring says a LAN `ollama.hosts[]` entry qualifies and only the ollama.com cloud should be excluded. As a result:
   - The constrained repair round is off for every LAN host. That is the owner's primary setup, a VM driving a LAN GPU host.
   - `halo doctor --local` reports "free-form JSON (host has no constrained-decoding support)" for a host that does support it.
   - The gym's repair runs unconstrained.

   — Verified: `is_local_host(OllamaHost(url="http://gpu-box.lan:11434"))` is False, so the gate returns False. — Fix: key the gate on "not Ollama Cloud" (host URL `ollama.com`, or an `api_key` present), never on loopback.

8. **major** — `halo_harness/agent/loop.py:796,2334-2368,2429,2121` + `providers/ollama_calibrate.py:167-277` — Auto-calibration runs synchronously inside `_build_ollama_body_for_ref`. That is the first request of a model on a host from any path:
   - the main turn;
   - compaction;
   - `call_small_model`, which serves titles, hooks, `/local <question>` on a worker thread, and the escalation judge.

   Problems with how it runs:
   - No abort is threaded in, so Esc waits for the whole calibration.
   - Each load is `_get_json(timeout=60)` plus `fetch_ps(timeout=60)`, and `call_small_model` starts its `timeout_s` timer only after the body is built.
   - The notice is queued and drained only after the calibration finishes (`:2585`, `:3929`), so the known follow-up "the notice must say how long it will take" cannot be met as wired.
   - Dedupe is per Session (`__init__`, `:796`), not "per process" as the comment says, so concurrent sub-agents on a new model calibrate it at the same time.
   - A failed or timed-out load counts as "not resident". An asleep host, or a big model that takes more than 60 s to load, therefore steps down to 4096 and records `does_not_fit` permanently: `has_calibration_entry` then never retries. The notice falsely says the model does not fit.

   — Verified by trace through the cited lines. — Fix: post the notice before calibrating, run it with the session abort and a total budget, skip it in `call_small_model`, distinguish "unreachable" from "not resident" (and record nothing on the former), and dedupe at module level.

9. **major** — `halo_harness/providers/ollama_calibrate.py:72-87,329-347` + `tui/dialogs/model_picker.py:235` + `roles.py:312` — The calibration store and the last-turn throughput record are keyed by the raw model string, with no `ollama_names_match`. So:
   - `halo ollama calibrate qwen3:latest` and an `ol:qwen3` session never see each other's entry. The session auto-calibrates again, with 2-3 more loads.
   - The panel, which looks up by the catalog's tagged name, shows "not calibrated" and no "last turn" line for anything a session recorded under an untagged ref.
   - The picker's capability lookup and `vram_aware_override` (`model == main_ref.raw`) also compare raw strings. The fix pass asked for exactly this grep.

   — Verified: record `qwen3:latest`, then `lookup_learned_cap(model="qwen3")` returns None and `has_calibration_entry` returns False. — Fix: normalize on write and on every read, in all five places.

10. **major** — `halo_harness/providers/ollama_calibrate.py:79-111` + `ollama_hw.py:671-683` + `agent/loop.py:2358-2362` — Commit 9af8dac says "a cap is re-measured when the digest or the Ollama version changes". Nothing re-measures automatically:
    - The auto gate is `has_calibration_entry`, which ignores digest and version. So after an `ollama pull` the cap is silently dropped (digest mismatch) and never measured again; Halo falls back to the arithmetic estimate of finding 3 indefinitely.
    - The hot path never passes `ollama_version`, so after an Ollama upgrade the stale cap keeps applying.

    — Verified: an entry with digest `old`, looked up with digest `new`, gives None while the gate still says "calibrated"; a lookup without the version still returns 32768. — Fix: gate auto-calibration on `lookup_learned_cap(..., digest, version)` (the version cached per host per process), and treat a stale entry as absent.

11. **major** — `halo_harness/providers/huggingface_local_resolve.py:177-251` + `huggingface_mlx.py:128-130` — A bare `hf:local/<model>` never uses `<model>` to choose the server:

Stale entries resolve to dead ports, and `ensure_mlx_server` "reuses" a dead mlx server indefinitely instead of starting one. `resolve_managed_server_by_model`'s own docstring describes this hazard. — Verified: with registry entries for modelA then modelB, `resolve_local_server(None)` for `hf:local/modelA` returns modelB's server. — Fix: resolve a bare ref by an exact registry model id first (with a liveness probe), then fall back to auto-detection; drop or restart dead entries.

13. **major** — `halo_harness/providers/local_use.py:193-197` + `local_runtime.py:81-90` — `halo local serve` passes `-c fit_estimate`, which is capped by neither the trained context nor the 131072 hard cap. 18. **minor** — `halo_harness/providers/local_runtime.py:202-204` + `local_use.py:135-203` — A second `halo local serve` (or `/local` `s`) of the same model starts another server and overwrites the first registry entry without stopping it.
