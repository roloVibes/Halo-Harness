## The items, with the pinning test each one needs

C1  Offline allow-list (`providers/http.py`, `providers/ollama.py`,
    `init_providers.py`). Offline mode is the user's network policy: only
    loopback, RFC1918/link-local/ULA addresses and hosts the user has
    explicitly marked local may be reached; `ollama.com` (the cloud Ollama
    entry keyed by `api_key`) and any other public hostname that happens to sit
    in `ollama.hosts`/`huggingface.local_servers`/endpoints is NOT local and
    must be refused under offline, with the same "offline mode" sentence the
    gate already uses. Follow the finding's fix text for the exact rule (a
    host is allowed when its URL resolves to a private/loopback address or the
    entry carries an explicit local marker; literal cloud hosts never). Test:
    under offline, `ollama.com` and a public hostname entry are refused, a LAN
    host entry and loopback pass, and the refusal sentence is the user-facing
    one.

C2  Proxy under offline (`providers/http.py`). With offline on, no connection
    goes through `HTTPS_PROXY`/`HTTP_PROXY`; loopback and private targets are
    always direct regardless of `NO_PROXY`. Test: offline + proxy env set ->
    the opener used is direct for a LAN/loopback target.

C3  The offline bypasses the gate never sees (`update.py` git ls-remote
    update check, `cc:`/`cx:` subprocess turns, `plugin_fetch.py` clone,
    `headless.py` background fetches, `hf:mlx` download): each must consult
    the same `network.offline` gate before starting and either skip with the
    offline sentence (background checks: silently skip, log at DEBUG) or
    return an error result (a `cc:`/`cx:` turn under offline cannot run; say
    so in one line). Test per site with the network stubbed: offline -> the
    subprocess/opener is never invoked; online -> unchanged.

C21 The remaining offline leak the finding names (read it; redirects or
    ssh or similar): close it the same way, pinned by one test.

C16 Secrets in `~/.halo/config.json` (`init_providers.py`, `theme.py`,
    `config_cli.py`): `ollama.hosts[].api_key`, `huggingface.endpoints[].token`,
    `huggingface.local_servers[].api_key` and any other secret-bearing field
    must be written with the same treatment the finding prescribes (the
    secret-store/env-reference path the rest of the config uses, 0600 on the
    file where the platform supports it, and `halo config show`/`/config`
    render them masked). Keep backward compatibility: an existing plaintext
    value still works and is migrated on the next write. Test: saving a host
    with an api_key leaves no plaintext key in the file (or whatever the
    finding's fix specifies), `config show` masks it, reading it back resolves

C17 Secrets in logs (`providers/huggingface.py`, `providers/ollama.py`,
    `bugreport.py`, `redact.py`): never log `%r` of a whole config entry; log
    the entry's name only. Extend `redact.py` so a bug report redacts `hf_...`,

    config entries. Test: a DEBUG log line for a malformed entry contains the
    name but not the key; `bugreport` output of a config with keys contains

## Hard constraints (from the owner; not negotiable)

  code, strings, docs or tests. Offline is described as the user's network
  policy, nothing else. Describe behaviour, never gate it.

- No network in tests; no downloads.

  docs lines that describe offline mode and secrets (docs/CONFIG.md).
