## The six items, with the pinning test each one needs

B1  `agent/subagent.py` child credentials. A child session resolves ITS OWN
    credentials for its model ref (`headless._resolve_creds(model_ref,
    parent.settings)` or the equivalent per-entry resolver the fallback chain
    already uses); the parent's creds, `openrouter_base_url` and
    `extra_headers` are reused only when provider and host match. A child whose
    creds resolve to None returns an `is_error` tool result naming the missing
    credential (the provider's own "not configured" sentence) instead of
    sending anything. Test: parent on `or:` with an OpenRouter key and an
    `X-HF-Bill-To` header; child `AgentSpec(model="ol:qwen3:8b")` must build
    with Ollama's base URL, no OpenRouter key and no bill-to header; child
    `oai:gpt-6-sol` with no OpenAI key must return the error result and make no
    request (stub the HTTP layer; assert zero calls).

B2  `controller.py` `set_model` + `agent/loop.py` `Session.set_model`. When
    the ref's creds do not resolve, `Controller.set_model` refuses and shows the
    provider's own not-configured sentence (exempt `cc:` and `cx:`, which need
    none); for an `hf:mlx/` ref it runs `_ensure_mlx_server_for_ref` first.
    `Session.set_model` CLEARS creds when given None instead of keeping the
    previous model's. Test: scratch `or:` session, `set_model("hf:local/x")`
    with no server and `set_model("oai:gpt-6-sol")` with no key -> model and
    creds unchanged, the refusal line queued; then prove `Session.set_model(ref,
    creds=None)` leaves no stale creds behind.

B3  `agent/codex_process.py` `build_cx_argv`: never emit `-s <mode>` after
    `exec resume <id>`; pass the sandbox as `-c sandbox_mode=<mode>` for BOTH
    the first turn and resumes (accepted by both subcommands). Make the fake
    codex used by the suite reject unknown flags after `resume` the way clap
    does (exit 2, "error: unexpected argument '-s' found") so this class of bug
    cannot pass again. Test: argv for resume contains no `-s` and contains
    `-c sandbox_mode=`; the fake rejects `exec resume <id> -s x`.

B4  Prompt delivery for `cx:` (`agent/codex_process.py`, `agent/codex_turn.py`,
    `providers/codex_models.py`). The prompt (preamble, carried conversation,
    user text, steer) is ALWAYS written to the subprocess's stdin, with the
    positional `-` (`codex exec ... -` and `codex exec resume <id> -`), never on
    argv; drop the 20,000-character argv cap (keep any cap that exists for the
    model's own context, but not an argv one); stdin must be a pipe, not
    DEVNULL. On Windows, when the resolved launcher is the npm `.cmd`/`.CMD`
    shim, launch `node <...\node_modules\@openai\codex\bin\codex.js>` directly
    (resolve the shim's target beside it; fall back to the shim only when the
    script is not found). Update the module docstring and docs/MODELS.md to
    match. Test: the fake codex reads the prompt from stdin and echoes it; a
    prompt containing `rename "foo & echo X" now`, `%USERPROFILE%` and 40,000
    characters arrives byte-for-byte; argv ends with `-`; a `.cmd` stand-in in
    a scratch dir with a `node_modules/@openai/codex/bin/codex.js` beside it
    resolves to the `.js` path.

B5  `providers/responses_request.py`: every Responses function-tool item
    carries `"strict": false` (Halo's schemas are not strict-form). Teach the
    Responses mock in the tests to enforce the strict rules (every property in
    `required`, `additionalProperties: false` on each object) whenever `strict`
    is absent or true, and reject with the provider's "Invalid schema for
    function" shape. Test: the 22 built-in tool items all carry strict false and
    the mock accepts them; an item without the key is rejected by the mock.

B6  `providers/profiles.py` + `providers/request.py`: `route.provider ==
    "openai"` gets its own chat-completions profile instead of the OpenRouter
    fallback: `max_tokens_field="max_completion_tokens"`,
    `stream_options: {"include_usage": true}`, `reasoning_effort` only when
    the vendored catalog row says `reasoning: true`, and
    `effort_values_supported` from the row's `reasoning_options` (so `max`
    clamps to the highest value the row lists, never to a value it does not).
    Test: bodies for `oai:gpt-6-sol` (reasoning), `oai:o3` with effort `max`,
    and `oai:gpt-4o` (no reasoning): assert the field names, the include_usage
    flag, and the presence/absence/clamp of `reasoning_effort`.
